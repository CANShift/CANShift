## 1. Critical findings (action immédiate)

### Firmware

#### F-CR-1 — Null-deref `s_pStatus` sur le chemin BLE CMD
`canshift-firmware/src/hal/ble/ble_server.cpp:357,363`

`CmdCallbacks::onWrite` appelle `s_pStatus->getSubscribedCount()` sans
null-check. `s_pStatus` est nul quand le setup GATT a échoué
(heap trop bas) ou après `BleServer::stop()`. Un client appairé qui
écrit `start_wifi_ap` après ré-init en mémoire dégradée → panic.

**Fix :** ajouter le garde déjà présent à `:674` (`if (s_pStatus && …)`)
et également garder `s_pStatus->notify()`.

---

#### F-CR-2 — Race read-modify-write sur `SignalStore::update`
`canshift-firmware/src/runtime/signal_store.cpp:85-101`

La fonction prend le spinlock, capture `wasValid`/`prevSmoothed`, libère
le lock, calcule l'EMA, **reprend le lock** pour écrire. Entre les deux
sections, un autre task écrivant le même `SignalId` (button optimistic
write côté UI, CAN task côté core 0) peut écrire dans le slot. Le second
writer voit son EMA écrasé.

**Fix :** maintenir le lock sur tout le RMW (FP sous spinlock — déjà
fait dans `setTimeout`/`checkTimeouts`), ou per-signal mutex, ou
`std::atomic<float>` + CAS.

---

#### F-CR-3 — `vQueueDelete` racing avec push CAN
`canshift-firmware/src/hal/usb/usb_comm.cpp:676-679` vs `:790`

`CMD_CAN_SCAN_STOP` (USB task) supprime la file, le CAN task (core 0)
peut envoyer entre son check `!s_canScanMode` et `xQueueSend` → send
vers handle libéré → corruption mémoire/crash.

**Fix :** `s_canScanMode = false` en premier, `vTaskDelay(1)` pour
drainer, puis `vQueueDelete`. Ou garder la file en vie tout le temps,
ne désactiver que via `s_canScanMode`.

---

### Core

#### C-CR-1 — Seuils `oil_press_bar` inversés dans `MAXXECU_SIGNALS`
`canshift-core/src/ecu-profiles/index.ts:199-201`

`warningLevel: 1.5, dangerLevel: 1.0`. Pour une alarme **low-side**, on
attend `dangerLevel ≤ warningLevel`. Préset built-in que les utilisateurs
sélectionnent dans une dropdown — la classification "value < warning →
amber, value < danger → red" saute direct du vert au rouge.

**Fix :** corriger les valeurs et ajouter un `.superRefine` cross-field
sur `SignalDefSchema` qui valide la relation
`min ≤ warningLevel ≤ max` (et idem pour `dangerLevel`), avec support
explicite des sémantiques high-side et low-side.

---

#### C-CR-2 — Test de chaîne de migration stoppe 3 versions sous CURRENT
`canshift-core/src/__tests__/migration-runner.test.ts:718,775-792,824-832`

`CURRENT_SCHEMA_VERSION = '1.17.0'` mais le test "full chain regression"
walke 1.0.0 → 1.14.0 avec une liste `applied` hardcodée. Les migrations
1.14→1.15, 1.15→1.16, 1.16→1.17 existent (`migration-runner.ts:78-121`)
mais ne sont **pas** exercées end-to-end. Un breaking change y est
invisible.

**Fix :** remplacer les littéraux `'1.14.0'` par `CURRENT_SCHEMA_VERSION`
et reconstruire `applied` programmatiquement depuis `BUILTIN_MIGRATIONS`.

---

### Mobile

#### M-CR-1 — Deux fetchers GitHub-releases parallèles
`canshift-mobile/src/services/ota.service.ts:134` &
`canshift-mobile/src/services/releases.service.ts:241`

`OtaService.fetchReleases` (flow OTA) et `ReleasesService.runFetch`
(écran About) frappent indépendamment `api.github.com/repos/…/releases`,
avec caches/retries/timeouts/validations différents. `OtaService` n'a
**pas** d'`AbortController` timeout, **pas** de gestion rate-limit, **pas**
de cache — il peut hang le flow OTA indéfiniment et double-facture la
limite GitHub 60 req/h.

**Fix :** promouvoir `ReleasesService` (impl plus robuste) en single
source. Adapter `ota-releases.store` pour le consommer via un mini-adapter
`ReleaseInfo → FirmwareRelease`.
